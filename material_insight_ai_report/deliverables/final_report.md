**과제명**: 관심 산업 기반 AI Agent 도입 전략 및 Delivery 설계
**주제 문장**: 나는 **건설 산업**의 **시공사 공정관리자(Project Controls Engineer/Scheduler)** 를 위해, **공정 지연 발생 시 Critical Path 영향 분석과 복구 대안 검토에 수일이 걸리는 업무 문제**를 해결하는 AI Agent를 설계·구현한다.

## 1. 주제 선정 배경

### 1.1 왜 건설 공정관리인가

건설은 대표적인 **저생산성·저디지털화 산업**이다. McKinsey Global Institute(2017)에 따르면 지난 20년간 글로벌 제조업의 노동생산성이 연 3.6% 성장하는 동안 건설업은 **연 1.0%** 성장에 그쳤고, 산업 디지털화 지수에서도 건설업은 농업과 함께 최하위권으로 분류된다[1]. 대형 프로젝트의 **98%가 비용 초과 또는 일정 지연**을 경험하고, 평균 일정 지연은 계획 대비 **20개월**에 달한다는 분석도 같은 보고서에 포함되어 있다[1].

일정 지연은 단순한 불편이 아니라 **직접적인 금전 리스크**다. 발주자와 시공자는 지연 발생 시 지연배상금(Liquidated Damages)과 공기연장(EOT, Extension of Time) 클레임을 두고 다투며, 이를 위한 국제 표준 실무 지침(SCL Delay and Disruption Protocol[2], AACE RP 29R-03 Forensic Schedule Analysis[3])이 별도로 존재할 정도로 일정 분석은 전문화되어 있다.

### 1.2 왜 "지연 복구 검토" 업무인가

시공 현장에서는 자재 납품 지연, 장비 고장, 재시공, 설계변경, 승인 지연이 상시 발생한다. 문제가 발생하면 공정관리자는 Oracle Primavera P6[4] 공정표를 열어 다음을 수작업으로 수행한다.

1. 이 문제가 **어느 Activity**에 해당하는지 찾는다 (수천~수만 개 Activity 중에서).
2. 해당 Activity가 **Critical Path 위에 있는지**, Total Float가 얼마인지 확인한다.
3. 회의록·공문·시공계획서 등 **근거 문서**를 뒤져 원인과 제약조건을 정리한다.
4. 복구 대안(작업조 증원, 자재 조기 확보, 순서 조정)별 **회복 효과를 시뮬레이션**한다.
5. 경영진·발주처 보고용 **검토 보고서**를 작성한다.

이 과정은 문서 탐색과 반복적인 What-if 계산이 대부분이며, 통상 반나절~수일이 소요된다. 반면 지연 대응은 빠를수록 복구 옵션이 많다. **"탐색·계산·문서화는 자동화하고, 판단은 사람이 한다"** 는 구조가 정확히 들어맞는 업무이므로 본 과제의 주제로 선정하였다.

### 1.3 컨설턴트 관점의 문제 정의

- **As-Is**: 지연 인지 → P6 수작업 탐색 → 문서 수작업 취합 → 수작업 What-if → 보고서 작성 (반나절~수일)
- **To-Be**: 자연어로 문제 입력 → Agent가 Activity 후보·근거 문서·CPM 영향·복구 대안 3개·보고서 초안을 수 분 내 제시 → **사람이 확인·선택·승인**
- **하지 않는 것**: P6 원본 자동 수정, 계약/안전/품질 판단의 자동 확정

## 2. 산업 및 업무 특성 분석

### 2.1 산업 구조와 이해관계자

건설 프로젝트는 다층 하도급 구조로 수행되며, 일정 정보는 이해관계자 사이의 핵심 커뮤니케이션 수단이자 계약적 증거다.

| 이해관계자 | 일정 관련 역할 | 관심사 |
|---|---|---|
| 발주처 (Owner) | 마스터 일정 승인, EOT 심사 | 준공일 준수, 지연배상금 |
| 감리/CM | 공정 진도 검측, 승인 | 계약 준수, 품질·안전과의 정합 |
| 시공사 현장소장 | 공정 총괄 의사결정 | 공기 내 준공, 원가 |
| **공정관리자/Scheduler (주 사용자)** | P6 공정표 작성·갱신, 지연 분석, 보고 | Critical Path, Float 관리 |
| 공사 담당자(공종별) | 실행, 작업일보 작성 | 작업 가능일, 선행조건 |
| 협력업체(하도급) | 공종별 시공, 자원 투입 | 투입 일정 예측 가능성 |

### 2.2 핵심 업무 프로세스와 도메인 개념

공정관리의 계산적 기반은 1959년 Kelley & Walker가 정식화한 **CPM(Critical Path Method)**[5]이다. 본 과제 구현의 일정 엔진도 동일한 정의를 따른다.

- **Forward pass**: ES(Early Start) = max(선행 EF + lag), EF = ES + 잔여기간
- **Backward pass**: LF(Late Finish) = min(후행 LS − lag), LS = LF − 잔여기간
- **Total Float** = LS − ES. **Float ≤ 0인 경로가 Critical Path**이며, 이 경로의 1일 지연은 곧 준공일 1일 지연이다.
- **선후행 관계**: FS(Finish-to-Start)가 실무의 대부분을 차지하며, SS/FF/SF와 lag가 보조적으로 쓰인다.
- **EOT/지연분석**: 지연의 책임 귀속과 공기연장 산정은 SCL Protocol[2]·AACE 29R-03[3]이 표준 실무 방법론을 제공하는 별도 전문 영역이다.

업무 유형을 분류하면 다음과 같다.

| 유형 | 예시 | AI 적합성 |
|---|---|---|
| 반복 업무 | 진도 입력, 주간보고 작성, Activity 검색 | 높음 (자동화) |
| 문서 중심 업무 | 회의록·RFI·NCR·공문·시공계획서 관리 | 높음 (RAG) |
| 계산 업무 | CPM, Float, What-if | 높음 — 단 **LLM이 아닌 결정론적 코드**로 |
| 판단 업무 | 복구안 채택, 안전/품질 승인, 계약 판단 | 낮음 (사람 고유 영역) |

### 2.3 주요 데이터

| 데이터 | 형태 | 특성 |
|---|---|---|
| P6 공정표 (Activity, Relationship, Calendar) | XER/XML/CSV 내보내기 | 구조화, 수천~수만 행 |
| 작업일보/공정회의록 | 비정형 텍스트 | 현장 사실관계의 1차 근거 |
| RFI/NCR/공문 | 반정형 문서 | 지연 원인·책임의 증거 |
| 시공계획서/승인문서 | 비정형 문서 | 작업 제약조건, 공기단축 가능성 |
| 계약서/클레임 기록 | 비정형 문서 | EOT 판단 근거 (민감) |

### 2.4 규제·보안 이슈

- 공정표와 지연 기록은 **클레임 소송의 증거**가 되므로 변조 불가능한 이력 관리(스냅샷 불변성)가 필요하다.
- 입찰가·원가가 연동된 일정 정보는 **영업비밀**이며, 프로젝트 간 데이터 격리가 필수다 — 본 구현은 모든 검색을 project_id로 스코프한다.
- 안전(중대재해처벌법)·품질 관련 판단을 자동화할 경우 책임 소재 문제가 발생하므로, 본 설계는 해당 판단을 **명시적으로 사람에게 유보**한다.
- 국내 정책 환경: 국토교통부 「스마트건설 활성화 방안」(2022)은 BIM·데이터 기반 건설관리 확산을 국가 과제로 제시하고 있어[6], 공정 데이터의 디지털화 기반은 확대되는 추세다.

## 3. 현재 AI 도입 현황

건설 일정·문서 영역의 대표 상용 사례 4건을 조사하였다.

### 사례 1 — nPlan (영국): 일정 리스크 예측

- **해결 문제**: 공정표의 낙관 편향 — 계획 단계에서 어떤 Activity가 지연될지 사전 식별
- **AI 기술**: 수십만 건의 실제 완료 공정표(XER)로 학습한 지도학습 기반 지연 확률 예측(ML forecasting)[7]
- **실제 사용자**: 발주처·시공사 리스크/공정 조직 (Network Rail, HS2 등 대형 인프라 발주처 적용 사례 공개)
- **기대 효과**: 리스크 기반 버퍼 배치, 낙관적 마일스톤의 조기 경보
- **한계**: 예측은 "확률"만 제공 — **지연이 이미 발생한 후의 복구 대안 수립**은 다루지 않는다. 학습 데이터가 없는 신공법에 취약.

### 사례 2 — ALICE Technologies (미국): 생성형 시뮬레이션 스케줄링

- **해결 문제**: 자원·순서 제약 하에서 가능한 공정 시나리오 탐색이 수작업으로는 소수에 그침
- **AI 기술**: 제약 기반 조합 최적화 + 시뮬레이션(수백만 시나리오 생성·평가)[8]
- **실제 사용자**: 대형 시공사의 계획 엔지니어 (사전 계획/재계획 단계)
- **기대 효과**: 공기·장비 조합 최적화, 재계획 소요 단축
- **한계**: 모델 구축 비용이 크고 사전계획 단계 중심 — **현장 문서 근거와 연결된 일상적 지연 대응**용은 아니다.

### 사례 3 — Buildots (이스라엘): 컴퓨터비전 진도 추적

- **해결 문제**: 진도 실측이 수작업 검측에 의존해 공정표와 현장 실제가 괴리
- **AI 기술**: 360° 카메라 영상 + 컴퓨터비전으로 설치 상태를 BIM/공정표와 자동 대사[9]
- **실제 사용자**: 현장 공사·공정 조직
- **기대 효과**: 진도 데이터 수집 자동화, 지연의 조기 감지
- **한계**: "무엇이 늦었는지"는 알려주지만 **"그래서 준공일에 얼마나 영향이고 어떻게 복구할지"** 는 사람이 별도로 분석해야 한다.

### 사례 4 — Document Crunch (미국): 계약 문서 리스크 검토

- **해결 문제**: 방대한 계약·시방 문서에서 지연 통지 기한 등 위험 조항 식별 지연
- **AI 기술**: LLM 기반 문서 분석·질의응답(RAG 계열)[10]
- **실제 사용자**: 시공사 계약·현장 관리자
- **기대 효과**: 통지 기한 미준수로 인한 클레임 권리 상실 방지
- **한계**: 문서 이해에 국한 — 공정표 계산과 연결되지 않는다.

### 종합: 시장의 빈 자리

| 구분 | 예측(nPlan) | 최적화(ALICE) | 진도(Buildots) | 문서(DocCrunch) | **본 과제** |
|---|---|---|---|---|---|
| 지연 **사후 대응** | △ | △ | ✕ | ✕ | **◯** |
| 현장 문서 근거 연결 | ✕ | ✕ | ✕ | ◯ | **◯** |
| CPM 영향 정량화 | △ | ◯ | ✕ | ✕ | **◯ (결정론적)** |
| 복구 대안 생성·비교 | ✕ | ◯(사전) | ✕ | ✕ | **◯ (사후·근거 기반)** |

기존 도구들은 예측·측정·문서를 각각 다루지만, **"지연이 발생한 순간, 문서 근거와 CPM 계산을 묶어 복구안을 검토"** 하는 일상 업무 구간은 공백이다. 이 구간이 본 MVP의 표적이다.

## 4. 향후 AI Agent 도입 후보 10개

건설 공정관리 도메인에서 도출한 후보 10개를 6개 기준으로 비교하였다. (난이도·위험도: 낮음/중간/높음, 데이터 접근성: 상/중/하)

| # | Agent 후보 | 대상 사용자 | 해결 문제 | 기대 효과 | 난이도 | 위험도 | 데이터 접근성 |
|---|---|---|---|---|---|---|---|
| 1 | **P6 지연 복구 Copilot (선정)** | 공정관리자 | 지연 시 영향분석·복구검토 수일 소요 | 검토 리드타임 수일→수십분 | 중간 | 중간 | **상** (CSV export + 현장문서) |
| 2 | 작업일보 구조화 Agent | 공사 담당자 | 일보의 비정형 텍스트로 집계 불가 | 진도·인원 자동 집계 | 낮음 | 낮음 | 상 |
| 3 | 공정회의록 액션아이템 Agent | 공정/공무 | 회의 결정사항 추적 누락 | 후속조치 누락 방지 | 낮음 | 낮음 | 상 |
| 4 | RFI 분류·회신초안 Agent | 공무/설계 | RFI 처리 지연이 곧 공정 지연 | 회신 리드타임 단축 | 중간 | 중간 | 중 |
| 5 | EOT 클레임 근거수집 Agent | 계약/공무 | 지연 증거를 사후에 소급 수집 | 클레임 증거 체계화 | 높음 | **높음**(법적) | 중 |
| 6 | 주간 공정보고 초안 Agent | 공정관리자 | 매주 반복되는 보고서 작성 | 작성 시간 절감 | 낮음 | 낮음 | 상 |
| 7 | 자재 납기 조기경보 Agent | 자재/공정 | 납기 지연 인지가 늦음 | 지연의 사전 감지 | 중간 | 중간 | 중(공급사 데이터) |
| 8 | 하도급 공문 분류·대응 Agent | 공무 | 공문 대응 기한 관리 부담 | 기한 준수율 향상 | 낮음 | 중간 | 중 |
| 9 | 설계변경 일정영향 스크리닝 Agent | 공정/설계 | 변경의 일정 파급 검토 지연 | 변경 영향 조기 정량화 | 높음 | 중간 | 중 |
| 10 | 안전 TBM 문서지원 Agent | 안전관리자 | 위험성평가 문서 반복 작성 | 문서 작성 부담 경감 | 중간 | **높음**(안전책임) | 상 |

### 우선순위 논리

선정 기준을 **(a) 문제의 금전적 크기, (b) 데이터 접근성, (c) 검증 가능성(정답이 존재하는가), (d) 위험 통제 가능성** 4가지로 두었다.

- #5(EOT)·#10(안전)은 효과가 크지만 법적/안전 책임 위험이 높아 MVP 부적합 — 오히려 **사람 판단 유보 원칙**의 근거가 되었다.
- #2·#3·#6은 난이도가 낮으나 효과가 문서 작성 시간 절감에 국한된다.
- **#1은 (a) Critical Path 지연 = 지연배상금 직결, (b) P6 CSV export와 현장 문서로 데이터 확보 용이, (c) CPM 계산은 수학적 정답이 있어 정확도를 100% 검증 가능, (d) 복구안 채택을 사람에게 유보하면 위험 통제 가능** — 4개 기준을 모두 충족하여 MVP로 선정하였다.

## 5. MVP Agent 선정 이유 및 정의

**Agent 이름**: P6 Schedule Recovery Copilot

**한 문장 정의**: 현장 문제를 자연어로 입력하면 관련 Activity와 현장 문서를 검색하고, 결정론적 일정 엔진으로 Critical Path 영향을 계산한 뒤, 복구 대안 3개와 근거가 연결된 검토 보고서를 제공하는 공정관리 보조 Copilot.

### 5.1 핵심 설계 원칙 (그리고 그 근거)

| 원칙 | 근거 |
|---|---|
| **일정 수치는 LLM이 아닌 Python 코드(CPM 엔진)가 계산** | LLM은 산술·그래프 추론에서 환각을 일으킨다. 일정 수치는 클레임 증거가 되므로 오차 허용이 0이어야 하며, CPM은 결정론적 알고리즘으로 정확히 계산 가능하다[5]. |
| **RAG는 근거 제공 전용, 수치 계산 금지** | 문서는 맥락·증거를 주지만 Float 계산의 입력이 아니다. 역할 분리로 환각 경로를 차단한다. |
| **P6 원본 자동 수정(writeback) 금지** | 공정표는 계약 문서다. 시스템은 "검토안"까지만 만들고 반영은 사람이 한다. |
| **복구안 채택·안전·품질·비용·EOT 판단은 사람** | 2.4절의 책임·규제 구조상 자동 확정은 위험하다(#5, #10 후보 분석 참조). |

### 5.2 MVP 범위

- **포함**: 프로젝트/스냅샷 관리, Activity·Relationship CSV import(FS 관계), TXT/MD 현장문서 RAG, 자연어 이슈 분석, CPM 영향 계산(START_BLOCK/DURATION_INCREASE), 복구 시나리오 정확히 3개, 규칙 검증, 독립 리뷰, Markdown 보고서, 전 과정 trace 저장
- **제외**: P6 writeback, 완전한 XER 파서, SS/FF/SF·복수 캘린더, 자원 평준화, 비용 산정, BIM 연동, 계약 책임 자동 판단

## 8. 기술 아키텍처

전체 다이어그램은 `diagram/architecture.md` 참조. 요약 흐름:

```text
사용자(자연어 이슈)
   │
   ▼
[입력 가드레일] 길이/인젝션 검사 ──── 위반 → FAILED
   │
   ├─▶ Activity 후보 검색 (pg_trgm, 어휘 검색)
   ├─▶ RAG 근거 검색 (pgvector: top20 → threshold 0.35 → metadata boost → top8)
   ▼
[Issue Mapping Agent · vLLM] 이슈 구조화 + 후보 재순위  → [출력 가드레일]
   ▼
[Human-in-the-loop 게이트] top1≥0.85 AND 격차≥0.10 AND 미완료 AND 스냅샷 존재?
   ├─ 불충족 → NEEDS_ACTIVITY_SELECTION (사람 선택 대기, 상태 저장)
   ▼ 충족(또는 사람 선택 후 재개)
[CPM 엔진 · NetworkX] baseline / impact 계산 (LLM 미개입)
   ▼
[Recovery Planning Agent · OpenAI] 복구안 정확히 3개 제안 → [출력 가드레일]
   ▼
[Rule Validator] Activity·근거 allowlist / action 화이트리스트 / 개수 검증
   ▼
[CPM 엔진] 시나리오별 회복일수 재계산 (LLM 제안값은 입력일 뿐)
   ▼
[Review Agent · vLLM, OpenAI fallback] 독립 검토·경고 (실패 시 needs_human_review=True 폴백)
   ▼
Markdown 보고서 (근거 chunk 인용 연결) + 전 과정 trace DB 저장 (13개 테이블)
```

구현 규모 실측: REST API 15개 엔드포인트, DB 테이블 13개, Alembic 마이그레이션 3개(운영 PostgreSQL 적용 완료), 자동화 테스트 **104개 전건 통과**.

이 구조는 LangGraph의 StateGraph(State=analysis_run 행, Node=파이프라인 단계, Conditional Edge=HITL 게이트, Interrupt/Resume=NEEDS_ACTIVITY_SELECTION→select-activity)와 동일한 패턴을 프레임워크 없이 구현한 것으로, 코드 전반에 해당 개념 매핑을 주석화하였다.

## 9. Human-in-the-loop 설계

### 9.1 자동 진행 게이트 (구현 완료, 테스트 7건)

Activity 자동 선택은 아래 4개 조건을 **모두** 만족할 때만 허용한다.

1. top1 confidence ≥ **0.85**
2. top1 − top2 confidence ≥ **0.10** (근소 격차 시 자동화 금지)
3. 해당 Activity가 완료 상태가 아님
4. 해당 Activity가 현재 스냅샷에 실존

하나라도 불충족 시 `NEEDS_ACTIVITY_SELECTION` 상태로 정지하고 후보 목록을 사람에게 제시한다. 실제 데모에서 "커튼월 **설치**(0.95)"와 "커튼월 **자재 납품**(0.85)"의 격차가 0.10이라 자동 선택이 거부되었는데, 이는 의도된 동작이다 — **두 Activity 중 무엇이 지연의 본질인지는 도메인 판단**이기 때문이다.

### 9.2 사람에게 유보되는 최종 판단

P6 반영 여부 / 복구 시나리오 채택 / 안전 승인 / 품질 승인 / 비용 승인 / 계약·EOT 판단. 보고서 말미에 이 목록이 항상 명시된다.

## 10. 위험 요소 및 통제 방안

### 10.1 위험-통제 매트릭스

| 위험 | 통제 (전량 구현·테스트 완료) |
|---|---|
| LLM의 일정 수치 환각 | 계산은 CPM 엔진 전담 + **출력 가드레일**이 LLM 원본 JSON에서 ES/EF/Float/recovered_days 등 금지 필드 검출 시 실행 차단 |
| 존재하지 않는 근거 인용 | **Evidence allowlist**: 인용 chunk_id가 실제 검색 결과 집합 밖이면 Rule Validator가 거부 |
| 잘못된 Activity 매핑 | confidence 이중 임계(0.85/0.10) + HITL 선택 |
| 프롬프트 인젝션 | **입력 가드레일**: 한/영 인젝션 패턴·길이(5~4,000자) 검사 후 위반 시 분석 미개시 |
| 허용되지 않은 복구 행위 제안 | action 화이트리스트(REDUCE_START_BLOCK/REDUCE_ACTIVITY_DURATION) 외 전부 거부 |
| 리뷰 모델 장애로 파이프라인 정지 | Reviewer 실패 시 OpenAI fallback → 그것도 실패 시 needs_human_review=True로 **보수적 폴백** |
| 프로젝트 간 정보 유출 | 모든 검색·조회를 project_id로 스코프 |
| 분석 재현성/증거성 훼손 | 스냅샷 불변 + agent 원문 출력·검색 trace·계산 결과 13개 테이블 영구 저장 |
| P6 오염 | writeback 기능 자체를 미구현 (설계적 배제) |

### 10.2 다층 방어 구조

동일 위험을 **프롬프트 지시(요청) → Pydantic 스키마(형식) → 가드레일(원본 검사) → Rule Validator(비즈니스 규칙) → 엔진 재계산(수치 무시) → HITL(최종 판단)** 6개 층이 중복 방어한다. 예컨대 Planner가 회복일수를 임의로 출력해도: 가드레일이 차단하고, 통과했더라도 엔진이 무시하고 재계산한다.

## 12. 기대 효과와 한계

### 기대 효과

- **속도**: 탐색·계산·문서화 자동화로 지연 검토 리드타임을 수일 → 수십 분 수준으로 단축 (복구 옵션이 살아있을 때 의사결정 가능)
- **증거성**: 모든 판단에 문서 chunk 인용이 붙은 보고서 → EOT/클레임 대비 기록 품질 향상[2][3]
- **일관성**: 담당자 역량 편차와 무관하게 CPM 계산이 항상 동일·정확
- **감사가능성**: 스냅샷·검색·에이전트 원문·계산의 전 과정 trace가 DB에 보존

### 한계 (정직한 명시)

1. **FS 관계·단일 캘린더만 지원** — SS/FF/SF, 복수 캘린더, 자원 평준화 미지원. 실제 P6 대비 계산이 단순화됨 (범위 명시로 통제).
2. **XER 직접 파싱 미지원** — CSV export 경유 필요.
3. **매핑 품질은 Activity 명명 품질에 종속** — 부실한 명명 체계 현장에서는 HITL 빈도 증가.
4. **문서가 없으면 근거도 없음** — RAG는 업로드된 문서 범위 내에서만 인용 가능 ("관련 근거 없음" 명시로 통제).
5. **업무 효과 지표는 파일럿 전 미실측** — 현재는 시스템 품질 지표만 실측 완료.

**확장 로드맵**: XER 파서 → SS/FF/SF·캘린더 → 진도 데이터 연동(Buildots류와 보완 관계) → EOT 근거수집 Agent(#5 후보)와의 연계.

## 13. 프로토타입 구현 결과 (데모)

본 과제는 설계에 그치지 않고 **전 구간을 실제 구현·검증**하였다. 저장소에서 재현 가능하다 (`demo/README.md`).

### 13.1 구현 범위

- React 프론트엔드: 데모 데이터 원클릭 로더 포함 4단계 워크플로

### 13.2 데모 실측 결과 (실서버·실모델 E2E)

| 이슈 구조화 | 공종 curtain wall / 위치 A-12F / 지연 10일 / START_BLOCK — 전항목 정확 추출 |
